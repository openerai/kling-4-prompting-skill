# Kling 4 프롬프트 디렉터

장면을 시간에 따라 연출하라. 등장 대상의 수·위치·행동, 카메라, 소리와
결말을 구체적으로 작성하라. 모델의 기능, 작성자의 연출 권장안, 실제 생성 결과를
구분하라. [공식 사양과 충돌 처리](references/capabilities.md)를 기본 근거로 사용하라.

## 1. 요청을 바로 작업 가능한 브리프로 바꾸기

- 이미 받은 정보와 첨부물을 재사용하라. 모드·조명·렌즈 등을 매번 설문하지 말라.
- 확정할 항목: 작업 목적, 참조물 역할, 변경 범위, 길이·비율, 원테이크/멀티샷,
  핵심 사건과 결말, 대사·음악·자막 요구. 결과를 좌우하는 누락만 짧게 물어라.
- 사용자 지정이 없으면 **10초·16:9**를 작성용 가정으로 삼아 필요할 때만 알리라.
  이는 플랫폼 기본 비율이 아니다. 공식 Omni 기본 비율은 Auto다.
- 일반 결과는 사용자 언어로 설명하고 **복사 가능한 최종 프롬프트 한 블록**으로
  제공하라. 제목·해설 생략 요청이면 블록만 반환하라. 언어·YAML·글자 수 지정을
  우선하라. 기술 사양표와 검증 메모를 생성 프롬프트 안에 무조건 넣지 말라.
- 생성 요청이 없으면 프롬프트만 작성하라. 생성 요청이면 현재 연결 도구의 정확한
  모델 ID·입력 스키마를 확인한 뒤 실행하라. 웹 기능이 MCP/API에도 있다고
  가정하거나 임의 파라미터를 만들지 말라. 제한이 다르면 차이를 알리고 지원되는
  경로를 택하라. 업로드 순서가 확인되지 않은 @번호는 임시 표기라고 밝혀라.

## 2. 경로·버전 선택하기

| 의도 | 작성 경로 |
|---|---|
| 텍스트 아이디어, 여러 이미지·영상·음성·요소 결합 | Omni Reference |
| 영상에서 동작·카메라·리듬만 빌려 새 장면 제작 | Omni Reference / recreation |
| 원본 영상의 일부만 수정 | Omni Reference / edit, `Edit @Video1.`로 시작 |
| 특정 시점의 실제 이미지 구도 고정 | Keyframes, 이미지 전용 |
| 이미지 한 장을 첫 프레임으로 사용 | Keyframes 또는 지원되는 Omni 첫 프레임 지정 |
| 30초·고해상도·첫/끝/중간 키프레임 | Kling 4.0 |
| 빠른 탐색이며 20초 이하·720p로 충분 | Kling 4.0 Flash; 사용자 버전 지정을 우선 |

**서로 다른 두 진입점의 입력을 한 작업으로 합치지 말라.** 영상/음성 참조가
필요한데 Keyframes도 요구하면 Omni에서 지원되는 프레임 역할을 쓰되 실제 지원을
확인하라. 별도 Keyframes의 정밀 시점 제어와 동일하다고 보장하지 말라. 양쪽이
필수라면 단계 분리를 제시하라. Keyframes에는 비디오·음성·참조 요소를 넣지 말라.

30초를 넘는 요청은 연결된 개별 클립으로 설계하라. **2분 확장은 출시 예정**으로
취급하라. Flash를 요청한 30초·4K·키프레임 작업은 그대로 지원된다고 쓰거나 몰래
20초로 자르지 말라. 원래 목표를 보존하는 일반 4.0 또는 분할 대안을 명시하라.
HDR은 현재 UI/도구 확인 전 사용할 수 있다고 확정하지 말라.

## 3. 레퍼런스의 역할과 우선순위 고정하기

실제 첨부물을 볼 수 있으면 먼저 확인하라. 보지 않은 얼굴·차량 구조·동작을
봤다고 하지 말라. 각 참조물에 역할과 적용 범위를 부여하라.

```text
@Image1 controls the lead character's identity, hair, proportions and full outfit.
@Image2 controls the environment layout, materials and lighting only.
@Video1 controls action timing and camera movement only.
Preserve the character design from @Image1 throughout.
```

- 외형 / 의상 / 배경 / 액션 / 카메라 / 편집 리듬 / 음색을 분리하라.
- 같은 속성을 두 참조물이 다르게 지정하면 사용자 지시와 주 역할을 기준으로
  충돌을 해소하라. 다른 영상의 인물·복장·배경이 불필요하게 유입되지 않게 하라.
- `@Image1`, `@Video1`, `@Element1` 등의 실제 태그를 사용하라. 음성 프로필의
  태그 형식은 UI/도구에서 확인하라. 파일명·URL을 자동 업로드된 자산처럼 쓰지 말라.
- 총 자산 수와 유형별 수를 함께 검사하라. 영상 참조·편집 원본·비디오 요소는
  **공유 영상 한도**로 계산하라. 동일 자산을 두 역할에 사용했다고 중복 집계하지
  말고 실제 업로드 슬롯 기준으로 계산하라. 상세 한도는 capabilities.md를 읽어라.

## 4. 장면을 연출하기

다음 순서로 필요한 항목만 작성하라. 단순 장면을 이 틀 전체로 부풀리지 말라.

```text
[Reference roles, if supplied]
[Scene, subject count, initial positions and visible material/light details]
[Total duration, aspect ratio, one continuous take OR numbered shots]
[Timed beats: subject action + observable result + camera response]
[Continuity / physical interactions that matter]
[Dialogue, ambience, SFX, music and requested on-screen text]
```

- 추상적인 '고급스러운', '시네마틱'만 쓰지 말고 광원 방향, 표면, 구도와
  피사체의 행동으로 번역하라. 렌즈·필름·색보정은 필요한 효과에만 붙여라.
- 한 구간에는 주행동 하나와 읽을 수 있는 결과를 배정하라. 시간 구간이 겹치거나
  비지 않게 총길이를 맞추고, 마지막 행동이 완결될 여유를 주어라.
- 원테이크는 하나의 연속 카메라 경로로 작성하라. 시간 비트는 컷을 뜻하지 않는다.
  자동 멀티샷과 충돌하지 않게 `One continuous take, no cuts.`를 명시하라.
- 멀티샷은 컷 수·구간·프레이밍·이어받는 동작을 구분하라. 2–6샷을 모델 상한으로
  쓰지 말라. 샷 수는 러닝타임과 행동의 가독성으로 결정하라.
- 빠른 액션은 초반부터 사건을 시작하고 동작의 준비→실행→접촉→반응을 연결하라.
  긴 감상·풍경 비트로 시간을 채우지 말라. 실시간 동작을 요청하면 긴 슬로모션을
  넣지 말라. 와이드샷으로 전신·거리·진행 방향을 읽게 하라.
- 얼굴·헤어·체형·의상·제품 형상과 수, 소품 손 위치, 진행 축·시선·광원·배경
  구조를 컷과 가림 전후로 유지하라. 스타일에 맞는 피부와 재료를 묘사하되 과도한
  잡티나 무조건적인 실사·그레인을 강요하지 말라.
- 물리와 공간의 난점은 [연속성·편집 지침](references/continuity-and-editing.md)을
  읽어라. 카메라 이동과 피사체 이동을 구별하고 접촉·무게·관성·가림을 설명하라.

## 5. 대사·음향·문자 처리하기

- 대사는 실제 발화 언어로 따옴표 안에 쓰고 화자 이름·외형 참조·음색·속도·감정을
  연결하라. 두 인물 대사는 발화 시간과 듣는 반응을 나눠라. 한국어를 음역하거나
  영어로 번역하지 말라. 특정 한국 사투리가 공식 지원된다고 단정하지 말라.
- 발화에 충분한 시간을 주어라. 단어/음절 속도 계산은 작성용 추정으로만 사용하고
  실제 발화·립싱크 정확도를 검증했다고 하지 말라.
- 대사·환경음·효과음·음악을 구분하라. 필요한 경우 스테레오 위치와 음량 우선순위를
  지시하라. 업로드 오디오는 **음성 프로필 참조용**이다. BGM/SFX 파일을 음성 입력에
  넣지 말라. 원본 음악의 정확한 유지·외부 트랙 사용은 별도 편집 경로로 처리하라.
- 후반 편집에서 별도 음악을 넣을 계획이면 생성 프롬프트에는 BGM 제외를 명시하고
  필요한 대사·환경음·효과음만 남겨라.
- 자막/음악이 불필요하면 `No subtitles. No background music.`를 넣어라.
  사용자가 요청한 자막·음악에는 해당 금지를 넣지 말라. 일반적인 긴 네거티브
  단어 목록을 기본값으로 추가하지 말라. 장면 특유의 중요한 배제나 스타일 혼합
  방지는 짧게 명시할 수 있다. 애니메이션은 필요하면 실사 혼합을 배제하라.
- 로고·간판·자막은 정확한 문자열, 위치, 재질, 나타나는 시점, 가독성을 지정하라.
  '자막 없음'은 제품 라벨/간판 금지가 아니다. 텍스트 렌더링 지원을 오탈자 없는
  결과 보장으로 바꾸지 말라. 필수 문자는 실제 결과에서 확인하라.

## 6. 편집·키프레임 특수 처리하기

**편집:** `Edit @Video1. Change [target] to [replacement]. Keep everything else
unchanged.`를 골격으로 쓰고 구체적인 보존 항목을 추가하라. 짧은 부분 수정은
변경·보존만 간결하게 작성하라. 재구성과 편집을 혼동하지 말라. 수정 대상이 카메라면
카메라까지 고정하라는 모순을 제거하라. 배경 교체와 재조명은 허용된 변경 범위 안에서
피사체 위치·행동·카메라·컷·시간을 보존하라. 원본을 실제로 보지 못하면 프레임별
액션을 지어내지 말고 보존 지시만 작성하라.

**키프레임:** 사용 가능한 이미지와 시각/순서를 매핑하고 그 사이의 물리적 경로를
설명하라. 최대 10장을 전부 채울 필요는 없다. 첫/끝 프레임만 있으면 그 둘을 연결하라.
중간 프레임은 필요한 사건 시점에 배치하라. 첫 키프레임의 비율이 출력 비율을
결정하므로 요청 비율과 다르면 모순을 알리고 준비 방식을 제시하라. 같은 첫/끝
이미지만으로 완벽한 루프가 보장되지 않으므로 속도·조명·동작 위상도 연결하라.

## 7. 전달 전 점검하기

1. 사용자 요구, 참조물 역할과 @번호, 변경/보존 항목이 맞는지 확인하라.
2. 버전·모드·길이·자산 한도·첫 키프레임 비율의 충돌을 고쳐라.
3. 시간 합계, 샷 수, 대사 배치, 손·소품·공간축·결말을 대조하라.
4. 원테이크/컷, 고정/이동 카메라, 음악/무음, 자막/금지 문구의 모순을 제거하라.
5. 프롬프트 검사와 실제 생성 품질 검사를 구분하라. 실제 영상을 생성·관찰하지
   않았다면 '품질 검증 완료'나 '일관성 보장'이라고 하지 말라.

복잡한 작업은 [계획 검사기](scripts/validate_plan.py)를 실행하라. 이 스크립트는
**내부 작성 계획**의 수치·타임라인을 검사하며 Kling API 스키마가 아니다.
의미·화질·정확한 토큰 수·계정별 제공 여부는 검사하지 못한다.

```bash
python3 scripts/validate_plan.py /path/to/plan.json
```
